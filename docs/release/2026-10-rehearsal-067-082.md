## Verdict: NO-GO as the files stand; GO once F1, F2 and F4 are applied first

All 16 migrations apply cleanly to a copy of prod. But the rehearsal found a live P0 on prod today, and two places where the release would leave prod weaker than dev:

1. **P0, live now (F1).** The storage policy `"Admins view all verification docs"` on `storage.objects` is `FOR SELECT TO authenticated USING (bucket_id = 'verifications')`. It has no admin check, so any signed-in user can list and download every ID document (15 objects today). No repo file creates or drops it, so it was made by hand, and 067 to 082 leave it in place. The app never needs it: admin pages sign these files with the service role (`app/api/admin/verifications/[id]/route.ts`). Drop it now, separately from the release, and treat it as a possible POPIA incident (check storage logs for reads by non-owners).
2. **077 E4/E10 do not take effect on prod (F4).** 077 drops the dev policy names. Prod has different names for the same policies, so on prod buyers can still insert `orders` with any seller, total and status, and users can still insert or update `listings`. That means self-publishing into the sitemap, search and Ubunye.
3. **Migration 035 never reached prod or dev (F2).** `smart_productions.submitted_at` and `idx_smart_productions_one_per_creator` are missing. Develop's `lib/supabase/queries/smartProductions.ts` writes and filters on `submitted_at`, so creator production submit and the 7-day auto-publish fail. Prod has 0 duplicate live rows per creator, so the unique index is safe.

With F1 to F4 first (run C), every migration and test passes, apart from fixture collisions with prod's stricter constraints. I traced each of those to a test fixture, not the app (T1 to T3).

drop policy if exists "Users view own verification docs" on storage.objects;

## Lock and risk impact

- **Transactions.** Every migration is a single BEGIN/COMMIT; a failure leaves nothing applied.
- **No rewrites.** No column type changes, no volatile defaults, no CONCURRENTLY. The biggest prod table has 155 rows, so locks last well under a second.
- **The real risk is lock queueing.** An ACCESS EXCLUSIVE request waiting behind a long transaction blocks every reader of that table until it is granted. Only 077 and 080 set a timeout, so pass one for the rest. At check time prod had no transactions open longer than one minute.
